# git-commit-convention

## 格式

个人开发随便写写没事，但团队协作时，强烈建议采用国际通用的 **Conventional Commits** 规范。它的基本格式如下：

```text
type(scope): subject
// 空一行
body
// 空一行
footer

```

---

## cheet-sheet

### ① 核心：Type（必须，表明这次提交的性质）

用一个简短的动词或标签来开头，常用的有以下几种：

| Type | 含义 | 使用场景 |
| --- | --- | --- |
| **`feat`** | 新功能 (Feature) | 增加了新特性、新接口、新页面 |
| **`fix`** | Bug 修复 | 修复了代码缺陷或系统漏洞 |
| **`docs`** | 文档修改 (Documentation) | 只是改了 Readme、注释或 API 文档 |
| **`style`** | 代码格式调整 | 不影响代码逻辑的改动（如空格、分号、格式化、缩进） |
| **`refactor`** | 代码重构 | 既没有加新功能，也没有修 Bug 的代码重写 |
| **`perf`** | 性能优化 (Performance) | 提升运行速度、减少内存占用等 |
| **`test`** | 测试相关 | 增加或修改单元测试、自动化测试代码 |
| **`chore`** | 杂务/构建工具 | 修改构建流、依赖库管理、脚手架配置等 |
| **`ci`** | 持续集成 | 修改了 GitHub Actions、GitLab CI 等配置文件 |

### ② 可选：Scope（作用域）

用括号包裹，说明这次修改影响的范围（如：`auth`, `order-api`, `readme` 等）。

### ③ 必须：Subject（简短描述）

用一句话总结这次修改，通常不超过 50 个字。

---

## 3. 示例

如果你用 `git commit` 打开了编辑器，你可以写出一个层次分明的标准 commit：

```text
feat(auth): 增加微信第三方登录功能

- 集成微信开放平台 SDK
- 新增微信登录的回调处理逻辑
- 优化了用户首次登录时自动创建账户的流程

Closes #1024

```

> **提示：** 最后的 `Closes #1024` ，在代码`合并到主分支`时， GitHub/GitLab 上编号为 1024 的 Issue 就会直接自动关闭 。

---

## 💡 编写 commit 的几条金律

1. **多提交，少憋大招：** 不要积累了一两周、改了几十个文件才提交一次。一个 commit 尽量只做一件事（比如只修一个 Bug，或只写一个新功能）。
2. **用动词开头：** 比如 `fix:...`、`add:...`、`refactor:...`，让人一眼看出你的“动作”。
3. **解释“为什么”而不是“怎么做”：** 代码本身已经展示了“怎么做”，commit 信息应该用来解释**为什么要改这里**，或者**改了之后解决了什么问题**。
